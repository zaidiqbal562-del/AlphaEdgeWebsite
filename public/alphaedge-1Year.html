SECTION ONEWhat this programme is

AI-900 is a single continuous year of instruction that takes a learner from writing their first function to deploying a governed, monitored, multi-agent AI system into a regulated financial environment.

It is the complete version. The two shorter AlphaEdge programmes each solve part of the problem — PE-200 teaches a market professional to direct AI systems, and QF-600 teaches quantitative modelling to a technical depth. AI-900 contains the full ground: everything in both, plus the entire modern applied-AI stack that neither has room for. Retrieval architectures. The Model Context Protocol. Agentic systems, memory and orchestration. Generative models beyond language. Reinforcement learning in full. Production engineering, observability, security and regulatory governance.

The programme is organised as four terms of thirteen weeks, containing thirteen modules. Every module ends in a working system that is reviewed and defended. A capstone runs for the final seventeen weeks in parallel with teaching.

The three commitments that define it

  • Nothing is assumed. A learner who has never written code and has never seen a matrix can enter Week 1 and follow every step. The mathematics is rebuilt from the beginning. No module opens by saying "you will recall from your undergraduate course".
  • Nothing is skipped. Section Fourteen of this document is a complete concept index — every named technique, architecture, protocol primitive, algorithm and failure mode the programme covers, listed so it can be checked line by line.
  • Nothing is unverified. Every model must beat a declared baseline. Every result must survive a validation procedure designed for financial data. Every system must ship with an evaluation harness. A demonstration that cannot be measured is not a deliverable.

SECTION TWOWhy this programme exists

Four gaps in how applied AI is currently taught. Each one produces a recognisable kind of failed practitioner, and AI-900 is designed against all four.

Gap one — the tool course produces someone who cannot debug

Short courses teach a framework. The learner can assemble a pipeline while the framework behaves as documented, and is helpless the moment it does not. They cannot read a stack trace into a cause, cannot tell a data problem from a model problem, and cannot evaluate whether a new library is better than the one they know. AI-900 teaches mechanism before tooling: backpropagation is implemented by hand before PyTorch appears, attention is built before a model is called, and a vector index is constructed before a vector database is used.

Gap two — the theory course produces someone who cannot ship

University sequences cover the mathematics rigorously and stop at the notebook. The graduate has never handled a malformed feed, never reconciled a position, never watched a model degrade in production, never written a monitoring alert, and has no idea what an audit trail is for. Term IV of AI-900 exists entirely to close this, and production work begins in Week 1 with version control and testing rather than being appended at the end.

Gap three — almost nobody teaches the new integration layer

The hardest and most commercially valuable problems in applied AI today are not model problems. They are integration problems: how a model reaches trustworthy information, how it calls a tool safely, how several agents coordinate without compounding each other's errors, how state persists, and how any of it is audited. Retrieval architecture, the Model Context Protocol, agent orchestration and context engineering are treated here as first-class engineering disciplines with three full modules, not as a closing lecture.

Gap four — validation is taught as an afterthought, and in finance that is fatal

In most domains an over-optimistic model is embarrassing. In markets it is expensive, and the mechanism is specific: overlapping labels leak information across cross-validation folds, and a researcher who tests many variants will find an apparently significant one by construction [López de Prado, 2018; Harvey, Liu & Zhu, 2016]. AI-900 teaches purged validation, deflation for multiple testing and pre-registration as core methodology in Module 6, then enforces them on every submission for the remaining thirty weeks.

The summary claim. There are good courses on machine learning. There are good courses on generative AI. There are good courses on quantitative finance. There is almost nothing that teaches all three as one continuous body of knowledge, with the modern integration layer included and with a validation standard strict enough for money. AI-900 is built to be that.

SECTION FIVEThe AlphaEdge method

Three proprietary frameworks structure the programme. Each is named, taught explicitly, and applied as a submission requirement rather than offered as advice.

FRAMEWORK ONEThe Four-Layer Framework

Every AI system built in this programme is decomposed into four layers, and work on a layer may not begin until the layer beneath it is demonstrably sound.

LayerQuestionFailure if neglected
L1 · SpecificationWhat exactly is being computed?The system answers a different question and nobody notices
L2 · GroundingWhere does the evidence come from?Confident fabrication of figures, dates and sources
L3 · VerificationHow do we know it is right?Silent degradation; no way to distinguish improvement from regression
L4 · GovernanceWhat happens under attack or misuse?Data leakage, manipulated output, regulatory exposure

FRAMEWORK TWOThe Research Protocol

Six mandatory steps on every quantitative submission from Module 6 onward: Register the hypothesis before touching data · Partition a sealed holdout opened once · Validate with purging, embargo and walk-forward only · Count every variant tested including abandoned ones · Deflate the performance statistic for the number of trials · Falsify in a written section titled Why this may not work.

E[max SRN] ≈ (1 − γ)·Z−1[1 − 1/N] + γ·Z−1[1 − 1/(N·e)] The expected best Sharpe ratio across N trials when there is no skill at all. With enough attempts this exceeds 1.5 on pure noise. It is the benchmark against which every result in AI-900 is judged [Bailey & López de Prado, 2014].

TERM II · MODULE 4 · WEEKS 14–17Supervised learning and ensembles

  • Support vector machines: maximum margin, the hinge loss, soft margin, the kernel trick, radial basis and polynomial kernels; support vector regression.

Ensemble methods

  • Why ensembles work: variance reduction, bias reduction, and the role of decorrelation.
  • Bagging and random forests [Breiman, 2001]; out-of-bag estimation; extremely randomised trees.

17WEEK

Model selection, tuning and calibration

Causal inference

  • The potential outcomes framework; the fundamental problem of causal inference; average and conditional treatment effects.

25WEEK

Validation that does not lie

  • Why standard k-fold cross-validation is invalid on overlapping financial labels; the mechanism of leakage.
  • Purging, embargo, walk-forward and combinatorial purged cross-validation — generating a distribution of backtest paths rather than a single number [López de Prado, 2018].
  • Labelling methods: fixed horizon, the triple-barrier method, meta-labelling, sample weighting by label uniqueness.
  • Fractional differentiation: retaining memory while satisfying stationarity.
  • Multiple testing and deflation: the expected maximum Sharpe ratio under the null, the deflated Sharpe ratio [Bailey & López de Prado, 2014], the probability of backtest overfitting [Bailey et al., 2016], the reality check and superior predictive ability tests [White, 2000; Hansen, 2005], the stationary bootstrap [Politis & Romano, 1994], and the argument that conventional significance thresholds are far too lenient for this field [Harvey, Liu & Zhu, 2016].

TERM IV · MODULE 11 · WEEKS 43–45The Model Context Protocol and tool infrastructure

The integration layer. MCP is an open standard for connecting AI systems to tools, data and prompts through a common interface, and it is taught here as a protocol to be implemented rather than a product to be consumed.

43WEEK

Protocol foundations and server construction

  • The integration problem MCP solves: without a standard, every model–tool pair is bespoke, and capability cannot be reused across applications.
  • Architecture: hosts, clients and servers; the one-client-per-server relationship; separation of the application from the capability provider.
  • Message layer: JSON-RPC request, response and notification; identifiers, error objects and the lifecycle of a call.
  • Connection lifecycle: initialisation, capability negotiation, protocol version agreement, operation, shutdown.
  • Server primitives: tools (model-invoked actions with typed input schemas), resources (application-controlled context identified by URI, with subscriptions and templates), and prompts (user-invoked templates).
  • Client primitives: sampling (a server requesting a model completion through the host), roots (filesystem or URI boundaries granted to a server), and elicitation (a server requesting structured input from the user mid-operation).

Ships: A working MCP server exposing tools, resources and prompts over a documented schema.

44WEEK

Transports, clients, authorisation and deployment

  • Transports: standard input/output for local processes, and streamable HTTP with server-sent events for remote servers; session management, resumability and message replay.
  • Building a client: server discovery and configuration, capability inspection, tool registration into a model context, result handling, timeouts, cancellation and progress notifications.
  • Authorisation: the OAuth 2.1 pattern for remote servers, resource indicators, token audience binding, scopes and consent, and credential storage.
  • Tool design as an engineering discipline: naming, description quality, input schema design, error message design, response shaping, token economy, idempotency and pagination — the factors that determine whether a model uses a tool correctly.
  • Operations: versioning, backward compatibility, registries and discovery, logging, tracing and observability of tool calls.
45WEEK

MCP security and the trust boundary

A protocol that lets a model invoke real actions on real systems is a security surface. This week is taught as an attack-and-defend laboratory.

  • Tool poisoning: malicious instructions embedded in a tool description or schema, read by the model as guidance.
  • Rug-pull mutation: a server that changes a tool's behaviour after the user has approved it.
  • The confused deputy problem: a server with legitimate privilege induced to act on an attacker's behalf.
  • Token passthrough and audience confusion: why a token issued for one service must never be forwarded to another.
  • Cross-server interference and tool shadowing; namespace collision; supply-chain risk in third-party servers.
  • Defences: least privilege and scoped roots, explicit user consent for state-changing calls, human-in-the-loop approval gates, input and output validation, allow-listing, sandboxing and process isolation, rate and budget limits, comprehensive audit logging.
  • Financial deployment: exposing read-only market and research capability while keeping any order path behind a separate, human-authorised boundary.

Module artefact: A hardened MCP server and client pair with authorisation, consent gates, audit logging, and a written threat model with a demonstrated attack and its mitigation.

Systems that plan, act, remember and coordinate. The hardest engineering in modern AI, because errors compound across steps rather than appearing in one place.

46WEEK

Agent architectures and reasoning loops

  • What makes a system agentic: autonomy over control flow, tool use, persistence across steps, and a goal rather than an instruction.
  • Core loops: the interleaving of reasoning and action [Yao et al., 2023]; plan-and-execute; reflection and self-critique; branching search over candidate plans [Yao et al., 2024].

  • Tool use: function calling, parallel calls, schema design, argument validation, tool selection under a large tool set, retrieval over tools.

47WEEK

Memory, context engineering and multi-agent systems

  • Memory architectures: working memory in the context window, episodic memory of past interactions, semantic memory of learned facts, procedural memory of learned routines; writing, retrieval, consolidation and forgetting policies.

  • Human-in-the-loop design: approval gates, interruption and resumption, editable plans, and escalation policy.
  • Orchestration frameworks compared on their actual abstractions rather than their marketing.
48WEEK

Agent evaluation, reliability and safety

  • Why agent evaluation is hard: non-determinism, multi-step trajectories, partial credit, and the difference between task success and process quality.
  • Trajectory evaluation: step-level correctness, tool-selection accuracy, redundancy, recovery from error, cost and step count per task.
  • Building an agent test harness: deterministic environments, replayable fixtures, simulated tools, seeded runs, regression suites in continuous integration.
  • Failure modes catalogued: infinite loops, goal drift, premature termination, hallucinated tool results, cascading error, reward hacking, over-permissioned action.
  • Guardrails: budget and step limits, action allow-lists, dry-run and simulation modes, output validation, kill switches, and irreversibility analysis of every action an agent can take.
  • Agentic security: prompt injection through tool output, exfiltration through tool arguments, and the lethal combination of private data access, untrusted content and external communication.
